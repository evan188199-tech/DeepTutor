## 2. 一页看懂 outbound 派发

`ChannelManager._dispatch_outbound`（`manager.py:409`，本节未注明的锚点均在 `manager.py`）是所有渠道共用的出口流水线：

- 取消息：`consume_outbound` 带 1s 超时轮询（`:422`）；未知渠道直接丢弃并告警（`:424-427`）。
- 投递开关：`_progress` 消息按渠道 `send_tool_hints/send_progress` 门控（`:429-433`，开关解析见 `_resolve_bool_override:283`，兼容 camelCase 别名 `:25-28`）。
- 合流：连续 `_stream_delta` 按 `(channel, chat_id)` + `_stream_id` 合并成一帧（`coalesce_stream_deltas:46`；`_stream_end`/`_stream_final` 升级进合并帧 `:80-84`）；积压的 `_progress`（含工具提示）合并为一条（`coalesce_progress_messages:103`；`_thinking_notice` 有独立生命周期，永不并入 `:133-136`）。
- 去重：非流式消息按 `(channel, chat_id, origin_message_id|message_id)` + 内容 sha1 指纹压制完全重复回复（`_should_suppress_outbound:382`，`_fingerprint_content:375`）；`_progress` 永不去重。
- 重试：`send_with_retry:155` —— 3 次指数退避（1s/2s/4s，`_SEND_RETRY_DELAYS:23`），**只有 deliver 抛异常才触发**；`CancelledError` 原样上抛保证优雅关停。
- 装配：`_init_channels:222` 只实例化 config 里 `enabled=true` 的渠道（键 = 模块名，来自 `model_extra`）；缺实现/依赖 → setup `unavailable`（`:246-249`）；构造异常 → `error`（`:278-281`）；`allow_from == []` → 拒启并标 `action_required`（`:264-273`）。投递开关是**每渠道**自己的（历史顶层键已废弃，`:256-263`）。
- 生命周期：`start_all:343` 先起派发任务再并发 `_start_channel:301`；`_start_channel` 用 `setup_revision` 区分"渠道自己报的状态"与"manager 兜底判断"（`:302-329`），启动异常时强制 `_running=False` 并落 `error`。`stop_all:358` 先停派发再逐渠道 `stop()`。
- 状态查询：`get_status:489` 合并 configured 状态与活实例状态，是 WebUI 渠道页的数据源。

## 4. 三处高风险差异（改代码前先读这里）

1. **发送失败语义不统一 —— manager 的重试只对一半渠道生效。** 契约要求 `send` 失败必须 raise（`base.py:162-164`），`send_with_retry`（`manager.py:155`）也只认异常。napcat（`napcat.py:446`）、telegram、discord 文本（`discord.py:160-162`）、mattermost（`mattermost.py:420-421`）、msteams（`msteams.py:269-276`）、weixin（缺 context_token 即 raise，`weixin.py:988-991`）是达标路径；而 dingtalk（失败仅记日志+发降级文案，`dingtalk.py:504-518`）、mochat（catch-all 吞异常，`mochat.py:409-410`）、zulip（API 返回非 success 只记 error，`zulip.py:749-750`）、slack 文件上传（`:165-173`）、whatsapp 断线（`whatsapp.py:112-114`）、wecom 缺帧（`wecom.py:382-385`）、qq 缺 client（`qq.py:143-145`）都静默失败 —— 这些通道的消息丢失不会重试、只能靠日志发现。给渠道补"可观测的失败"时，先确认走的是哪条路径。
2. **流式缓冲键控：feishu 是唯一按 `_stream_id` 键控的实现，且是唯一实现 `consume_stream_delivery` 的渠道。** `base.send_delta` 的 docstring 明文要求"stateful 实现必须按 `_stream_id` 而非仅 chat_id 键控"（`base.py:176-179`）。feishu 做到了：`_stream_key:455` 让 narration 每轮一张卡、finish 轮的卡才是正式回复（`feishu.py:1615` docstring）。telegram/discord 的缓冲 dict 都以 chat_id 为键，仅在新 buf 建立时校验一次 stream_id（`telegram.py:697-704`、`discord.py:215-222`）——同一 chat 上两段流交错时（如上一段 `_stream_end` 迟到），后写者会拿到前者的 buf。另外 `_streamed` 最终稿的"确认后才免发普通稿"机制（`base.py:269-274`）只有 feishu 的 `consume_stream_delivery:466` 接了：其余渠道若未来启用 `_streamed` 路径，确认函数缺省返回 False，会自动回落普通 send，不会重复——这是安全默认，但意味着"已流式送达"无法被其他渠道声明。
3. **双重启动与 stop 语义：三个"非标准关停"案例。** ① feishu：lark `ws.Client.start()` 是永不返回的 `_select()` 且无 stop（`feishu.py:638-647` 注释 + 上游链接），唯一正确关停是取消 SDK 挂起的任务再关连接（`_shutdown_ws_client:291`）；如果只 `join` 线程不取消，僵尸连接会继续在同一 app id 下收事件——同一应用出现两个监听者。② dingtalk：`stop:213` 置位、关 http、取消后台任务，但**不取消正被 `start()` await 的 `_client.start()` 协程**（`:194`），监听要等 SDK 自身出错才会退出重连环。③ msteams：渠道自己 bind 端口（`msteams.py:228`），同一 Partner 被二次装配会直接 `OSError: address in use` 并以 setup error 呈现。其余 WS 渠道（telegram/qq/napcat/whatsapp/discord/mattermost/matrix）都是"`while self._running` 重连环 + stop 置位关资源"的标准形态，但它们对"start() 被调用第二次"均无守卫——重复启动由 manager 的单实例装配（每渠道一个实例、`start_all` 只起一次，`manager.py:343-356`）兜住，不要在渠道层再开第二个 start 任务。

## 5. 新增渠道 checklist

1. **模块与类**：在 `deeptutor/partners/channels/` 建模块，定义**恰好一个** `BaseChannel` 子类（registry 取第一个子类，`registry.py:38-47`）；helper 函数别写进同文件或独立成无子类模块。模块名 = config 键 = `channel.name` 三者保持一致（manager 按 config 键查 discovered map，`manager.py:243`）。
2. **配置模型**：继承 `DeliveryOverrides`（自动获得 send_progress/send_tool_hints，`deeptutor/partners/config/schema.py:15`）；要流式再叠加 `StreamingSupport`（`schema.py:28`）并真的覆盖 `send_delta`（`supports_streaming:183` 用"是否覆盖"判定，声明了却不实现会被静默当成不支持）。config 基类同时收 camelCase/snake_case（`schema.py:9-13`）。提供 `default_config()` 返回 `model_dump(by_alias=True)`（`base.py:253-256` 模式）。
3. **start()**：先查可选依赖（未安装 → `set_setup_state("unavailable")`，参照 `qq.py:87-93`）；再查必填字段（→ `action_required`）；置 `self._running = True`；长驻逻辑放 `while self._running` 重连环，正确传播 `asyncio.CancelledError`（参照 `whatsapp.py:81-82`）。收到消息一律走 `_handle_message`（ACL 在里面，`base.py:225`），**不要**直接 `bus.publish_inbound`。
4. **send()**：失败 raise（§4-1）；长文本按平台上限切分；媒体失败不要静默——要么 raise、要么并入正文的可见失败标记（matrix 模式，`matrix.py:478-483`）。
5. **stop()**：幂等；取消自己创建的所有 task/thread/定时器，关闭 http/ws；需要状态落盘的在 stop 里完成（weixin/mochat 模式）。
6. **入站去重**：平台层普遍会重推，用有界 deque/OrderedDict（1000–2000）按 message_id 去重（`qq.py:81`、`napcat.py:80`、`feishu.py:2342-2348`）。
7. **setup 状态词汇表**：`connecting / connected / running / action_required / error / unavailable / disconnected / waiting_for_scan(带 qr_payload)`——WebUI 按这套渲染，别发明新词（`base.py:74-87`；manager 兜底语义见 `manager.py:301-341`）。
8. **测试**：新建 `tests/services/partners/test_<name>_channel.py`；横切契约（重试/合并/去重/流式）已有 `test_channel_manager.py`、`test_partner_outbound_delivery.py`、`test_channel_streaming.py`（内含 discord/telegram/feishu 三实现对照），schema 面有 `tests/api/test_partners_channel_schema.py`。
9. **依赖声明**：requirements 分 extras（pyproject `# Partner channel SDKs` 注记，`pyproject.toml:178` 起）；渠道内用 `try: import … except ImportError` + `*_AVAILABLE` 或 `importlib.util.find_spec` 探测（`qq.py:15-24`、`wecom.py:17`、`feishu.py:29`）——ImportError 会被 registry 收集并在 UI 显示"为什么 X 不见了"（`registry.py:73-90`）。
